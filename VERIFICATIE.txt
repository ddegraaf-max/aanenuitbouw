DEPLOY CRASHED — OORZAAK EN OPLOSSING (ronde 17)
================================================

DE OORZAAK
==========
Uit je eerdere log:

  npm error command failed
  npm error signal SIGTERM

Bij elke deploy sluit Railway de oude container af met SIGTERM. Dat is normaal.
Maar jouw startcommando is `npm start`, en npm verpakt `node server.js`. Als npm
een signaal krijgt, sluit hij af met een foutcode. Railway ziet een niet-nul
exitcode en stuurt een "Deployment crashed"-mail voor wat in werkelijkheid een
nette herstart was. Elke deploy = één crashmail.

GEMETEN
=======
  oude server.js, rechtstreeks gestart, SIGTERM   -> exitcode 143
  nieuwe server.js, rechtstreeks gestart, SIGTERM -> exitcode 0
  oude server.js via npm start, SIGTERM           -> exitcode 143
  nieuwe server.js via npm start, SIGTERM         -> exitcode 143

Die laatste regel is belangrijk, en hij weerlegt wat ik eerst dacht. Ik zei dat
ik het in de code zou oplossen zodat het niet van een Railway-instelling
afhangt. Dat is niet waar: met npm ertussen krijgt Node het signaal NIET eens.
In de log staat de regel "SIGTERM ontvangen" dan helemaal niet -- npm vangt het
signaal zelf op, sluit af met 143, en het Node-proces eronder wordt gedood.

Er zijn dus TWEE dingen nodig, en de eerste is de belangrijkste.

STAP 1 — VERPLICHT: NPM UIT DE KETEN HALEN
==========================================
Railway → je service → Settings → Deploy → Custom Start Command:

    node server.js

Daarmee draait Node als hoofdproces en krijgt het het stopsignaal direct.
Je package.json hoeft niet te veranderen; het start-script blijft bruikbaar voor
lokaal gebruik. Bijkomend: de verwarrende "npm warn config production" in je log
verdwijnt ook.

STAP 2 — DE CODE: NETJES AFSLUITEN
==================================
In server.js staat nu een afhandeling voor SIGTERM en SIGINT:

  - lopende verzoeken worden afgemaakt (server.close)
  - inactieve keep-alive-verbindingen gaan direct dicht
  - daarna exitcode 0
  - noodrem: hangt er toch iets, dan na acht seconden alsnog met code 0, want
    Railway wacht niet veel langer voordat het proces alsnog wordt gedood

Zonder stap 1 doet dit niets, want dan bereikt het signaal Node niet. Met stap 1
erbij is de afsluiting nette én snel.

Ook toegevoegd: afhandeling van uncaughtException en unhandledRejection. Die
laten het proces WEL stoppen met code 1 -- een echte fout moet als crash
zichtbaar blijven -- maar schrijven eerst de volledige stack naar de log. Anders
verdwijnt de oorzaak in de opstartruis en heb je aan de crashmail niets.

WAT JE HIERNA ZIET
==================
  normale deploy  ->  "SIGTERM ontvangen — server sluit af, lopende verzoeken
                      worden afgemaakt" en "Alle verbindingen afgehandeld",
                      GEEN crashmail
  echte fout      ->  crashmail, en in de log "ONVERWACHTE FOUT — server stopt"
                      met de volledige stack

Daarmee is het verschil tussen een herstart en een storing weer uit je
monitoring te lezen. Dat was het punt: een melding die altijd afgaat, negeer je
op een dag precies wanneer het wel echt is.

MOCHT HET NA STAP 1 TOCH TERUGKOMEN
===================================
Dan is het geen rollover maar een echte crash. Kijk in Railway bij Deployments
naar het tijdstip en vergelijk dat met de deploy-log. Staat er
"ONVERWACHTE FOUT — server stopt" met een stack, stuur die dan; daar staat dan
precies in welk bestand en op welke regel het misgaat.
